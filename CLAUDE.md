Merchant Risk Sentinel — Permanent Project Instructions
1. Project Objective

Build Merchant Risk Sentinel, a Track 2 AI Risk Manager that detects:

suspicious individual transactions,
abnormal customer behavior,
abnormal merchant/payment-terminal behavior,
emerging fraud patterns over time,

and produces an explainable risk assessment with bounded defensive recommendations.

The goal is to build a credible, explainable, demonstrable risk-intelligence product, not simply a fraud-classification model.

2. Source of Truth

Use the following hierarchy:

Current phase-specific instructions — immediate instructions for the work being performed.
Master Merchant Risk Sentinel Development Plan — architecture, scope, roadmap, and frozen decisions.
Official Fraud Detection Handbook documentation/source — authority for dataset semantics.
Existing repository code — preserve working implementation unless there is a concrete reason to change it.

Do not silently change the project's architecture, dataset, technology stack, or scope.

If a genuine technical blocker requires a change, stop, explain the issue, propose the change, and wait for confirmation.

3. Frozen Dataset Decision

Use the Fraud Detection Handbook simulated dataset as the primary dataset.

Do not replace it with the user's previous PCA-transformed fraud dataset.

The Handbook dataset provides the foundation for:

transaction-level fraud detection,
customer behavioral analysis,
terminal/merchant behavioral analysis,
temporal fraud detection,
scenario-specific evaluation.

Treat it explicitly as simulated benchmark data, never as real Razorpay production data.

4. Core Architecture

Maintain separation between:

Data
 ↓
Feature Engineering
 ↓
Transaction ML Risk
 +
Customer Behavioral Risk
 +
Terminal Behavioral Risk
 ↓
Risk Aggregation
 ↓
Alert / Policy Engine
 ↓
AI Risk Analyst
 ↓
Dashboard / Audit Trail

Do not collapse these components into one opaque model.

The ML/statistical system determines risk.

The LLM explains evidence and recommends bounded actions.

The LLM does not independently determine fraud or execute financial actions.

5. Temporal Integrity

Temporal correctness is non-negotiable.

Never use:

future transactions,
future customer/terminal statistics,
future labels,
post-event information,
TX_FRAUD as a predictive feature,
TX_FRAUD_SCENARIO as a predictive feature.

Every historical feature must represent information that would genuinely have been available at the time the transaction was scored.

Use chronological evaluation rather than a random train/test split for the final system.

6. Engineering Principles

Always:

inspect existing code before modifying it;
make modular changes;
reuse working components;
avoid unnecessary dependencies;
keep raw data immutable;
maintain raw → processed → feature → model lineage;
make important transformations reproducible;
write tests for critical logic;
document important decisions;
handle missing data and cold-start cases explicitly;
use environment variables for secrets;
never commit credentials.

Do not build unnecessary infrastructure merely because it is technically possible.

7. ML Principles

Prioritize:

interpretability + correctness + measurable performance

over unnecessary model complexity.

Evaluate using appropriate fraud metrics, especially:

Precision
Recall
F1
PR-AUC
ROC-AUC
False Positive Rate

Do not use accuracy as the primary success metric.

Thresholds must be selected using validation data, never the final test set.

Keep model versions, feature versions, thresholds, and evaluation periods traceable.

8. Behavioral Risk Principles

Customer and terminal risk must be based on historical behavioral baselines.

The system should detect changes such as:

NORMAL
 ↓
RISK RISING
 ↓
HIGH RISK
 ↓
RECOVERY
 ↓
NORMAL

Do not permanently classify a customer or terminal as malicious because of one historical event.

The system must account for temporary fraud and concept drift.

9. Explainability

Every important risk/alert must have evidence.

Prefer explanations such as:

Risk increased because:

• transaction amount deviated from customer baseline
• terminal velocity increased
• recent terminal fraud rate increased
• unusual customer activity increased

Do not allow the LLM to invent evidence.

If an explanation cannot be supported by computed system data, it must not be presented as fact.

10. AI Risk Analyst

The LLM receives structured evidence generated by the system.

It may:

summarize the situation;
explain why risk increased;
identify important evidence;
recommend a bounded defensive action.

It may not:

fabricate metrics;
change risk scores;
override deterministic policy;
execute financial actions;
invent missing information.

LLM output must be structured and validated.

If the LLM fails, the core risk system must continue functioning with deterministic evidence/fallback behavior.

11. Defensive Actions

Use bounded actions such as:

ALLOW
MONITOR
STEP_UP_VERIFICATION
TEMPORARY_REVIEW
ESCALATE

The policy engine remains deterministic.

The LLM can recommend an action, but the system determines whether that action is allowed.

12. Testing

Every phase must leave the project in a testable state.

At minimum:

validate data assumptions;
test critical transformations;
test temporal leakage;
test APIs when introduced;
test model inference when introduced;
test end-to-end flows before final demo.

Do not consider a phase complete simply because code executes successfully once.

13. Phase Workflow

Work one phase at a time.

At the beginning of every phase:

PHASE START
→ inspect repository
→ inspect previous phase outputs
→ understand current state
→ identify required inputs/outputs
→ implement only the current phase

At the end:

PHASE COMPLETE
→ report files changed
→ report functionality
→ report tests/results
→ report metrics where applicable
→ report limitations
→ report blockers
→ wait for next phase

Do not automatically start the next phase.

14. Avoid Scope Creep

Do not prematurely add:

deep learning,
graph neural networks,
Kafka,
Kubernetes,
unnecessary microservices,
complex autonomous agents,
large rule engines,
real payment integration,
real customer/merchant credentials.

Only add complexity when there is a demonstrated requirement or measurable benefit.
