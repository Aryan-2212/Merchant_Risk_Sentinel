# TERMINAL_BEHAVIORAL_REPORT.md — Phase 6 Real-Data Run

Generated by `scripts/09_terminal_behavioral_report.py` against the full frozen
1,754,155-row Fraud Detection Handbook dataset (public simulated benchmark, per Dev Plan
§2 — not real Razorpay production data). `mrs.behavioral.terminal` was run **once** over
the full concatenated train+validation+test set (never per-split — a terminal's history
and state genuinely continues across split boundaries, exactly as Phase 3's
`build_feature_frame` is itself built once over the complete dataset before ever being
split). `terminal.py` was not modified for this run.

## 1. Run parameters

- Total rows processed: 1,754,155
- Distinct terminals: 10,000
- Date range: 2018-04-01 00:00:31 → 2018-09-30 23:59:57
- Runtime: **2.40s** (731,373 rows/sec — a single forward pass with dict-based

- Thresholds used (unchanged from the approved design): `MIN_TERMINAL_HISTORY=10`,
  `RISING_THRESHOLD=0.05`, `HIGH_RISK_THRESHOLD=0.15`, `RECOVERY_CONFIRM_THRESHOLD=0.0`,
  `RECOVERY_CONFIRM_COUNT=3`

**Observation**: `RISK_RISING` is rare (120 transactions, 23 terminals ever reached it)
relative to `HIGH_RISK` (17,322 transactions, 2,986 terminals). This is the expected,
documented consequence of the approved direct-jump rule
(`NORMAL/INSUFFICIENT_HISTORY → HIGH_RISK` when deviation exceeds 0.15 in one step): real
compromise episodes in this dataset drive the recent fraud rate far above the moderate
0.05–0.15 band, so most genuine escalations skip past `RISK_RISING` entirely rather than
pausing there. `RISK_RISING` is effectively only reached by moderate blips that don't
escalate further — which are uncommon in this dataset's actual fraud dynamics.

## 4. Behavioral episodes

An "episode" = a maximal contiguous run of a terminal's transactions in one of
{RISK_RISING, HIGH_RISK, RECOVERY} (i.e., from first elevation until confirmed return to
NORMAL, or the terminal's data ends).

| | Value |
|---|---|
| Total elevated episodes | 3,656 |
| Episodes that reached HIGH_RISK | 3,647 (99.75%) |
| Episodes that resolved at RISK_RISING only | 9 |
| Episode length (transactions): median / mean / max | 6.0 / 7.9 / 63 |
| Episode duration (hours): median / mean / max | 115.4 / 183.1 / 1519.6 |
| HIGH_RISK-reaching episode duration (hours): median / mean / max | 115.5 / 183.4 / 1519.6 |

**Comparison to known ground truth** (`docs/DATASET_REPORT.md` §5, measured independently
in Phase 2 from labeled-fraud-day contiguity, a different but related methodology): 2,353
real Scenario-2 episodes, median length ≈2 days (48 hours), max 27 days (648 hours).

- The engine detected **3,656 episodes** — more than the 2,353 real ones. This is
  consistent with, and explained by, the terminal-level precision finding in §5 below
  (many detected episodes are triggered by an isolated Scenario-1/3 fraud transaction
  passing through an otherwise-uncompromised terminal, not a genuine Scenario-2 episode).
- The engine's median detected duration (115.4h ≈ 4.8 days) runs longer than the real
  median (~2 days). This is an expected consequence of two deliberate design choices, not
  a bug: (1) `terminal_fraud_rate_deviation` is itself a *24-hour rolling* signal, so it
  takes up to 24h after the last actual fraud transaction for the recent rate to fully
  decay; (2) `RECOVERY_CONFIRM_COUNT=3` requires three additional calm transactions
  before declaring full recovery, adding further deliberate hysteresis on top.
- The max detected episode (1519.6h ≈ 63 days) is more than double the longest single
  real episode (27 days). `docs/DATASET_REPORT.md` §5 notes some terminals were
  compromised **more than once, at different times** — if a terminal relapses from
  `RECOVERY` back into `RISK_RISING`/`HIGH_RISK` before completing its confirmation
  streak, the engine correctly treats this as one continuous, still-unresolved episode
  rather than two separate ones. A single very long detected episode is a plausible,
  defensible reading of a terminal with an unresolved, repeatedly-relapsing compromise
  pattern — not necessarily a stuck state machine — but is flagged here as worth watching
  if Phase 6 is extended further.

## 5. Validation against known Scenario-2 (compromised terminal) labels

`TX_FRAUD_SCENARIO` was used **only** for this post-hoc validation printout — it is never
read by `mrs.behavioral.terminal`, which sees no label column at all (verified in the
prior design review and by the module's own source).

### Transaction-level detection

| | Value |
|---|---|
| Total Scenario-2 fraud transactions | 9,077 |
| ...flagged elevated (RISK_RISING/HIGH_RISK/RECOVERY) at that moment | 8,298 (91.42%) |
| ...flagged specifically HIGH_RISK at that moment | 8,208 (90.43%) |

**This 90.4% transaction-level Scenario-2 detection substantially exceeds Phase 5
XGBoost's own Scenario-2 recall of 59.3%.** This is the central validation result of
Phase 6: a simple, non-ML, threshold-based statistical engine, using a signal
(24h-vs-historical fraud-rate deviation) already computed in Phase 3, detects
compromised-terminal fraud far more sensitively than the transaction-level model alone —
directly confirming the architectural premise that terminal behavioral risk is a
necessary *complementary* signal, not a redundant one, and giving Phase 5's documented
Scenario-2 weakness a concrete, working complement rather than requiring Phase 5 itself
to be reworked.

### Terminal-level detection (computed for this report; not part of the persisted script output)

| | Value |
|---|---|
| Terminals ever genuinely Scenario-2 | 357 |
| Terminals ever flagged HIGH_RISK | 2,986 |
| Overlap (true positives) | 351 |
| Genuine Scenario-2 terminals missed entirely | 6 |
| **Terminal-level recall** | **98.3%** (351/357) |
| **Terminal-level precision** | **11.75%** (351/2,986) |

**This is the most important honest finding in this report and must not be understated.**
Recall is excellent — the engine finds nearly every genuinely-compromised terminal at
least once — but precision is low: roughly 7 out of 8 terminals that ever reach
`HIGH_RISK` were never actually part of a labeled compromise. This is not a code defect;
it is the expected, mechanistically-explainable consequence of a deliberately sensitive
single-signal, threshold-based detector:

- Scenario-1 (high-value) and Scenario-3 (compromised customer) fraud can occur at *any*
  terminal, not just compromised ones. A single such fraud transaction passing through an
  otherwise-normal, moderate-or-lower-volume terminal can be enough to push that
  terminal's 24h recent fraud rate 15+ points above its own historical baseline purely
  because the 24h window has few enough transactions for one fraud event to dominate it.
- Confirming this mechanism directly: of the 17,322 transactions flagged `HIGH_RISK`,
  **51.88% (8,987) are genuine, non-fraudulent transactions**, 47.38% (8,208) are real
  Scenario-2 fraud, and the remainder are Scenario-1/3 fraud (0.06%/0.68%). The majority-
  genuine composition is *expected and correct*, not alarming on its own: `HIGH_RISK` is
  a **terminal-level behavioral state**, not a per-transaction fraud classifier — once a
  terminal enters an elevated window, every transaction that terminal processes during
  that window (fraudulent or not) correctly inherits the elevated context, because the
  claim being made is "this terminal's *behavior* is currently anomalous," not "this
  specific transaction is fraud." Combining that context with the transaction-level
  XGBoost score is exactly what a later Risk Aggregation phase is for (Dev Plan §13,
  Phase 6 handoff §15 boundary) — Phase 6 deliberately does not attempt that combination
  itself.

## 6. Cold-start handling

106,794 transactions (6.09%) were `INSUFFICIENT_HISTORY` — every terminal's first ~10
transactions (or however many transactions until `terminal_hist_fraud_rate` becomes
defined), consistent with 10,000 terminals × up to 10 initial transactions each. No
terminal ever produced a confident behavioral score before accumulating sufficient
history (Dev Plan §28).

## 7. Limitations

- **Low terminal-level precision (11.75%)** at the current thresholds — by design a
  sensitive-first detector; not tuned for precision, and not intended to be the final
  word on a terminal's status (that is Risk Aggregation's job, a later phase).
- Episode durations run longer than the raw labeled-fraud-day ground truth due to the
  24h rolling window's inherent decay lag plus the deliberate 3-transaction recovery
  confirmation — both intentional hysteresis, not bugs, but worth knowing when
  interpreting "how long was this terminal considered at risk."
- The longest detected episode (63 days) may reflect a genuinely unresolved,
  repeatedly-relapsing compromise pattern, or may indicate the confirmation mechanism is
  slow to fully clear for certain low-volume/erratic terminals — flagged for attention if
  Phase 6 is extended, not resolved here.
- This report is a static, whole-dataset run, not a streaming/replay demonstration —
  the replay-style "watch a terminal's state evolve in real time" scenario (Dev Plan §22,
  §23 Demo 3) remains for a later phase.
- Thresholds (`RISING_THRESHOLD`, `HIGH_RISK_THRESHOLD`, `RECOVERY_CONFIRM_COUNT`, etc.)
  were chosen as documented, interpretable project defaults informed by the dataset's
  measured ~0.8% baseline fraud rate — they were not grid-searched or tuned against this
  real-data run's own outcome (Dev Plan §46: measure, then decide, without chasing a
  target metric after the fact).
